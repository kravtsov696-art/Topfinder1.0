## ADR-API-1: node:http вместо Fastify/NestJS

ТЗ предлагает Fastify или NestJS «с обоснованием». Для P0 выбран встроенный `node:http` + маленький роутер (`apps/api/src/http.ts`, ~150 строк):
- 20 эндпоинтов, без плагинов, сессий, шаблонов — фреймворк не даёт заметной пользы;
- одна внешняя зависимость сервера (`postgres`) — минимальная поверхность для supply-chain-рисков и быстрый холодный старт;
- серверные тесты идут по настоящему HTTP на настоящей БД.
Переход на Fastify в P1 механический: обработчики уже изолированы (`router.add(method, path, auth, handler)`).

## Модель данных

`users` → `devices` (токен — SHA-256, режим OFF/ECO/ACTIVE_TRIP, отчёт о разрешениях) → `invites` (хэш кода, TTL 10 мин, одноразовый) → `pairs` (инициатор, принявший, срок, отзыв) → `pair_grants` (направленное разрешение owner→viewer, **по умолчанию выключено**, `enabled_since`) → `location_fixes` (measured_at ≠ received_at, точность, источник, состояние приложения/сети, качество, `late`, `scenario`) → `refresh_requests` + `refresh_request_events` (автомат) → `diagnostic_events`.

## Правила доступа (проверяются на каждом запросе)

1. Токен устройства → устройство не удалено.
2. Пара: устройство — участник (иначе 404), не отозвана, не истекла, собеседник не удалён (иначе 403).
3. Чтение точки собеседника: его grant → мне включён **и** его режим ≠ OFF; выдаётся только последняя точка качества `accepted/low_quality`, измеренная не раньше `enabled_since − 2 мин` и не старше TTL.
4. Запрос обновления: те же условия; иначе запрос фиксируется как `access_denied`, без «успеха».
5. Экспорт — только свои данные; полный экспорт — только с `ADMIN_TOKEN`.

## Геолокационный движок (телефон)

- Источник точек — `Location.startLocationUpdatesAsync` (системные обновления), а не таймер.
  - **ECO**: `Balanced`, ≥ 50 м, Android ≥ 60 с; на Android — foreground service с уведомлением (переключателем можно сравнить без него).
  - **ACTIVE_TRIP**: `BestForNavigation`, ≥ 10 м, Android ≥ 5 с, iOS — синяя плашка фоновой геолокации, Android — уведомление «Активная поездка до HH:MM»; автоматический возврат в ECO.
  - **OFF**: задача остановлена, очередь очищена, сервер отклоняет точки (`sharing_off`).
  - `pausesUpdatesAutomatically: false` задан явно: в нативном коде expo-location на iOS по умолчанию `true`, хотя документация пишет `false`.
  - На iOS expo-location вместе со стандартными обновлениями включает **significant-change monitoring** (видно в `EXLocationTaskConsumer.m`) — это может перезапускать приложение после выгрузки/«смахивания» при заметном перемещении. Проверяется сценарием 4.
- Токен хранится в Keychain с `AFTER_FIRST_UNLOCK` — иначе при заблокированном iPhone фоновая задача не прочитает токен.
- Очередь: ≤ 500 точек; старше 24 ч — удаляются с записью в журнал; повторы 15 с → 15 мин (с разбросом), ≤ 60 попыток; при возврате сети — сразу; `measuredAt` неизменен; сервер дедуплицирует по `clientFixId` и сортирует по `measured_at`.
- Запрос обновления у целевого телефона: опрос `incoming` каждые 4 с при открытом приложении; в фоне — сервер возвращает открытые запросы в ответ на очередную фоновую отправку точки (`fix_response`). Ответ — новое измерение (`getCurrentPositionAsync`, таймаут 30 с) или точка возрастом ≤ 15 с (помечается). Push — этап D.
- Геозона-эксперимент: `startGeofencingAsync`, 150 м, вход/выход пишутся в журнал как «системное событие», не как подтверждённый факт.

## Что сервер хранит и чего не делает

- TTL точек 24 ч (`LOCATION_TTL_HOURS`), журнал 7 дней, связи 14 дней; очистка раз в минуту.
- В логах сервера: метод, шаблон пути, статус, время. Без тел, токенов, координат.
- **E2EE не реализовано**: координаты защищены TLS и проверкой доступа, но сервер их видит. Это осознанное решение P0 (блупринт §10.2).
