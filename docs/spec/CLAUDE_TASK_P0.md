# Задание для Claude Code: P0 — реальный тест геолокации iPhone ↔ Android

**Контекст:** основной проект — «Близкие», доверенный обмен геолокацией. В перспективе существует отдельный продукт «Люди рядом», но его НЕ разрабатывать сейчас. Вложение `LOCATION_PROJECT_BLUEPRINT_v1.md` — исходная проектная спецификация (разделы 4.1, 7, 17–19, 23 особенно важны). Если вложения нет, работай по требованиям ниже. При противоречиях между ранними гипотезами и действующими ограничениями платформ документируй расхождение и выбирай проверяемое, безопасное решение.

## Твоя роль и результат

Ты — ведущий разработчик мобильных приложений, backend-инженер и инженер по тестированию. **Нужно не описание идеи, не макет и не обещание, а исходный код рабочего экспериментального приложения** и инфраструктуры, позволяющих проверить качество работы геолокации на двух реальных телефонах: одном iPhone и одном Android.

В конце должны существовать: репозиторий с кодом, инструкция запуска, сервер, две устанавливаемые тестовые сборки *если среда и учётные записи позволяют*, тестовый протокол, средства измерения и честный отчёт о том, что фактически собрано и проверено. Если iOS-сборка невозможна без Apple signing/macOS/учётной записи, предоставь готовый проект и точные следующие команды/действия; **не заявляй, что iOS проверена, если не проверена**.

**Центральный критерий продукта:** карта отличает достоверную свежую координату от устаревшей, приблизительной, недоступной или не полученной. Никогда не изображай старую координату как текущую.

## Границы P0

Сделать только испытательный модуль «Близкие» для двух добровольно подключённых взрослых тестовых устройств. Никаких знакомств, поиска незнакомых людей, массовых аккаунтов, монетизации, детского режима, Bluetooth-сети, сложной истории перемещений и обещаний экстренного поиска. Данные из P0 не использовать в будущем продукте знакомств.

### 1. Технологический подход

- Предпочтительно монорепо: `apps/mobile` (React Native + TypeScript, Expo **Development Build**, не Expo Go), `apps/api` (Node.js + TypeScript; Fastify или NestJS с обоснованием), `packages/shared` (контракты и типы), `docs/` (сборка, эксперименты, ограничения), `scripts/` (выгрузка результатов). Выбирай поддерживаемые совместимые версии зависимостей и фиксируй их в lockfile.
- PostgreSQL + PostGIS в Docker Compose для координат/событий, без Redis, микросервисов и шардирования до появления измеренной необходимости. Если для самых первых локальных smoke-тестов нужен упрощённый backend, не выдавай его за финальный, а сохрани совместимый API.
- Мобильный UI общий; геолокация — через официальные механизмы iOS/Android. Допускаются Expo Location/TaskManager для первой реализации и нативные модули Swift/Kotlin там, где API действительно нужны и JS-слой не справляется.
- Для обмена — HTTPS API; при открытой карте допустим polling/SSE. Для запросов к устройству в фоне исследовать APNs/FCM; **не предполагать, что обычный push гарантированно разбудит любое приложение**.
- Должна быть возможность развернуть тестовый backend с публичным HTTPS-адресом, доступным по сотовой сети; секреты и учётные данные только через env/secrets. В документации дать локальный запуск и путь к тестовому удалённому серверу. Не требовать, чтобы телефоны находились в одной Wi-Fi-сети.

### 2. Минимальные экраны

1. **Моё устройство:** статус геолокации, разрешения (foreground/background, точная/приблизительная, когда ОС позволяет определить), GPS/сеть, режим обмена `OFF / ECO / ACTIVE_TRIP`, последние координаты только самому владельцу, `accuracy` в метрах, время получения на устройстве и время приёма сервером.
2. **Подключение второго телефона:** однократный код или QR с коротким TTL; владелец второго телефона явно подтверждает обмен. Оба устройства могут видеть друг друга; обмен по умолчанию выключен. Видимые кнопки «Включить обмен», «Остановить», «Разорвать связь».
3. **Карта пары:** обе точки, только последняя разрешённая позиция, круг погрешности, момент измерения, возраст точки, статус `свежая / устаревшая / приблизительная / недоступна`. Фиксировать собственные пороги как экспериментальные, не как гарантию ОС. Если точка устарела, не анимировать её как живую.
4. **Запросить обновление:** показать конечный автомат запроса: `создан → принят сервером → передан push-провайдеру (если применимо) → получен устройством (только при явном подтверждении) → измерена точка → точка доставлена` либо `таймаут / отказ / доступ запрещён / причина неизвестна`. Не подменять подтверждение APNs/FCM подтверждением телефона. Для режима «оба приложения открыты» реализовать настоящий рабочий запрос и ответ.
5. **Диагностика и экспорт:** временная шкала событий; экспорт CSV/JSON для сравнения устройств без необходимости копировать данные вручную. Названия событий и причин понятны человеку.

UI утилитарный, не трать время на графический дизайн. Русский язык интерфейса достаточен.

### 3. Геолокационный движок

- Источник событий: нативные/системные обновления координат и разрешённые события перемещения, а НЕ жёсткий таймер «каждые N секунд всегда».
- Режим `OFF`: нет новых передач; нельзя читать чужие данные после отзыва доступа. `ECO`: минимизировать пробуждения и энергию; `ACTIVE_TRIP`: пользователь явно включает более активный обмен на ограниченное время, с видимым индикатором.
- Записывать измерение (`fix_time`), поступление серверу (`server_received_at`), accuracy, поставщика/тип измерения, возраст, состояние приложения и сети **только если платформа даёт эти сведения**. Не выдумывать доступность GPS, состояние OS scheduler, или причину фоновой паузы.
- Защита качества: валидация диапазонов lat/lon, accuracy, повторов, аномально будущих timestamp, неверного порядка поступления. Поздно доставленная старая точка не должна заменить более свежую по моменту фактического измерения.
- При отсутствии сети: локальная ограниченная очередь с оригинальными временными метками, синхронизация после возврата сети, backoff, без бесконечных попыток и утечек данных. Точки, срок действия которых истёк, должны обрабатываться как исторические или отбрасываться по документированной политике.
- Для iOS корректно оформить background location permissions/configuration. Для Android проверить granular location permissions, foreground service типа location в допустимых случаях и требования к уведомлению. Не применять скрытые обходы энергосбережения или запретов пользователя.
- **Отдельный технический эксперимент (не блокер базовой сборки):** iOS Location Push Service Extension (LPSE). Сначала проверить реальные требования entitlement, APNs, Always authorization, подписания и поддержки выбранным стеком. Если доступно — реализовать минимальную нативную ветку и измерить; если недоступно — документировать blocker и fallback. Не изображать LPSE реализованным, если этого нет. Аналогично на Android оценить FCM + допустимые сценарии получения координаты в фоне; push не равен праву запустить фоновый location foreground service.
- По возможности добавить один тестовый geofence с ручным включением/выключением и логированием входа/выхода (не раньше, чем заработают основные отправка/приём точек).

### 4. Backend, доступ, безопасность

- Разделить сущности `user`, `device`, `pair_grant`, `location_fix`, `refresh_request`, `diagnostic_event`. У каждой позиции есть `device_id`, measured_at, received_at и accuracy; у связи — срок действия, инициатор и явное принятие.
- Минимальная тестовая авторизация с защищёнными токенами и хранением на устройстве. Одноразовые коды/QR ограничены по времени и по количеству попыток; не использовать открытый эндпоинт, позволяющий по device_id получить чужие координаты.
- Проверять разрешение на **каждом** чтении координат, запросе обновления и получении истории/экспорта. Отзыв сразу блокирует последующие API-запросы. Добавить серверные негативные тесты на чужой ID и на отзыв.
- TLS, секреты не в репозитории, минимум диагностических данных в серверных логах, точные координаты не отправлять в crash/analytics. На P0 явно указать, что **E2EE не реализовано**, если применяется обычное серверное шифрование/защита доступа.
- Понятное добровольное согласие и постоянный способ выключить передачу. TTL для тестовых геоданных (например, 24 часа по умолчанию) и механика удаления данных. Не встраивать скрытый режим наблюдения.

### 5. API и тесты

Выработай и документируй контракт: привязка тестовых устройств; выпуск и принятие одноразового приглашения; выдача/отзыв grant; запись location fix; чтение последнего доступного fix; создание и отслеживание запроса обновления; получение диагностических событий; экспорт результатов; удаление данных. Идентификаторы запросов и идемпотентность обязательны.

Автотесты: права доступа, отзыв, TTL, попытка чтения чужой точки, сортировка отложенных координат по measured_at, invalid accuracy/lat/lon, clock skew, повторная доставка, истёкшее приглашение, таймаут remote refresh. Добавить smoke-тест сервера и проверку TypeScript/линтинга. Не маркировать моковые тесты как пройденные испытания реального GPS.

### 6. Реальный план испытаний на двух телефонах

Нужен воспроизводимый протокол для iPhone и Android, с колонками: модель телефона, версия ОС, версия сборки, разрешения, точная/приблизительная геолокация, Wi-Fi/сотовая сеть, энергосбережение, сценарий, количество запросов, число полученных точек, `fix_time`, `received_at`, погрешность, задержка, успешность запроса обновления, признаки сбоя, расход батареи (с отдельно описанной методикой и контрольным сценарием).

Проверки:
1. Оба приложения открыты, неподвижно и при перемещении.
2. Один экран заблокирован, затем оба.
3. Приложение свёрнуто на 10–30 минут.
4. Пользователь принудительно закрывает приложение (особенно отдельно отметить отличие iOS/Android).
5. Телефон перезагружен, приложение не открывалось.
6. Нет сети 5–15 минут, затем сеть вернулась: очередь и исходные временные метки.
7. Выключено разрешение на геолокацию; выдано только приблизительное; энергосбережение.
8. Улица, помещение, транспорт/перемещение при согласии обоих участников.
9. Нажатие «Запросить обновление» при открытом и фоновом приложении; точный статус каждой попытки.
10. Разорвать связь и убедиться, что новые запросы больше не раскрывают координаты.

Экспортировать сырые **локальные** тестовые события по согласию, таблицу результатов и краткую сводку: success rate, p50/p90 задержки по сценариям, время устаревания, расход батареи относительно контроля. Там, где выборка мала, явно написать, что вывод предварительный; **не ставить заранее гарантированные проценты или интервалы**.

### 7. Порядок выполнения и проверяемые артефакты

Выполняй реальную работу в такой последовательности:

**Шаг A — каркас.** Посмотри исходную спецификацию; зафиксируй выбранные версии и ограничения; создай монорепо с README, конфигурацией и запуском API/БД.

**Шаг B — работающий прямой обмен.** Сделай сопряжение телефонов, явное включение передачи, получение и отображение координат при открытых приложениях, статусы точности/свежести. Реализуй запрет доступа после revoke.

**Шаг C — фон и диагностика.** Добавь реальные системные background updates по возможностям ОС, диагностический журнал, очередь при offline, экспорт и ручной remote refresh со статусами.

**Шаг D — нативные расширения.** Исследуй/при доступных предпосылках реализуй LPSE на iOS, Android FGS/FCM и тестовую геозону. Не блокируй завершение рабочего базового обмена недоступным entitlement.

**Шаг E — проверка и передача.** Запусти доступные команды, зафиксируй их точный вывод/результат. Дай инструкции сборки/установки `Android APK` и `iOS development build/TestFlight` по реальным возможностям окружения. Подготовь `TEST_MATRIX.md`, `RUNBOOK.md`, `KNOWN_LIMITATIONS.md`, `IMPLEMENTATION_STATUS.md`, `ARCHITECTURE.md`, `.env.example` и инструкции получения CSV/JSON.

### 8. Жёсткие критерии приёмки

P0 готов к **полевым испытаниям**, когда:
- обе тестовые установки (либо код iOS-проекта с подтверждённой сборкой на соответствующей среде) имеют понятный путь установки;
- приложения при явном согласии реально обмениваются точками через защищённый сервер;
- карта отображает точность, фактическое время измерения, последнее обновление и честный статус устаревания;
- новый доступ нельзя получить по знанию только ID устройства; отозванный grant блокирует дальнейшую выдачу;
- ручной запрос обновления имеет реальные состояния и таймаут, не показывает фиктивный успех;
- данные сохраняют исходное measured_at при offline/retry, а запоздалая точка не подменяет свежую;
- диагностика экспортируется, а протокол испытаний позволяет проверить заблокированный экран, фон и потерю связи;
- есть результаты реально запущенных автоматических тестов и реестр того, что на физических телефонах ещё не проверено.

**P0 эксперимент завершён** только после испытаний на реальном iPhone и Android и заполнения матрицы. Доступность кода/макета/симулятора — не доказательство работы в фоне на физических устройствах.
